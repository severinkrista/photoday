# Шаг 1. Архитектура Android-приложения «Фото дня / задачи» и интеграция с Яндекс Диском

## 1. Цель первого этапа

Нужно создать Android-приложение, в котором можно быстро зафиксировать выполненную задачу:

- вид задачи — из редактируемого пользователем списка;
- сложность — субъективная оценка от 0 до 5;
- краткое описание;
- возможность изменять набор атрибутов задачи в будущем;
- сохранение записи в таблицу, расположенную именно на Яндекс Диске.

Ключевое ограничение проекта: **Яндекс Диск является целевым и основным хранилищем данных**. Не планируем переносить данные в собственную БД, Firebase, Google Drive, сервер или другой облачный сервис.

---

## 2. Что уже есть в репозитории

В ветке `main` находится существующее Windows-приложение на Python/Tkinter.

Основные особенности текущей реализации:

- `main.py` — главное окно и управление потоком приложения;
- `ui_components.py` — элементы интерфейса и создание записи;
- `file_operations.py` — сохранение в TXT/XLSX;
- `settings.py` + `state.py` — настройки;
- `data_processing.py` — обработка данных;
- `statistic.py` — статистика;
- приложение уже умеет сохранять рабочие записи в текстовый файл и Excel.

Android-версию не следует делать переносом Tkinter/Python. Логичнее использовать существующую бизнес-идею и модель данных, но построить отдельное нативное Android-приложение.

Ветка для новой разработки: **`yadisk`**.

---

## 3. Предлагаемый фундамент

### Язык

**Kotlin**

Причины:

- основной современный язык разработки Android;
- хорошо работает с корутинами;
- удобен для сетевого кода;
- хорошо интегрирован с Android Jetpack.

### UI

**Jetpack Compose**

Использовать Compose вместо XML-layouts.

Основные экраны:

1. Экран добавления задачи.
2. Экран/диалог управления видами задач.
3. Экран настройки Яндекс Диска.
4. При необходимости — экран последних операций синхронизации.

Интерфейс должен быть ориентирован на максимально быстрое внесение записи: открыл → выбрал вид → поставил сложность → написал пару слов → сохранил.

### Архитектура

Предлагается разделение:

```
UI (Compose)
    ↓
ViewModel
    ↓
Use Cases
    ↓
Repositories
    ↓
Yandex Disk API / XLSX processor
```

Основные слои:

- `presentation` — Compose + ViewModel;
- `domain` — модели и бизнес-правила;
- `data` — работа с Яндекс Диском, XLSX и настройками;
- `core` — общие утилиты, ошибки, логирование.

Не делать UI напрямую ответственным за HTTP или Excel.

## 4. Главный технический вопрос — таблица на Яндекс Диске

Здесь есть важная особенность.

Яндекс Диск предоставляет REST API для работы с файлами и их содержимым. API предназначен в том числе для мобильных приложений. Есть также WebDAV API. citeturn1search3turn0search2

При этом Яндекс Диск — это прежде всего файловое хранилище. Поэтому для нашей задачи нужно разделять:

1. **Яндекс Диск** — где физически хранится файл;
2. **XLSX** — формат таблицы;
3. **Android-код** — который изменяет XLSX перед отправкой обратно на Диск.

Яндекс Диск поддерживает редактирование XLSX через свой редактор, поэтому XLSX является подходящим целевым форматом. citeturn0search6

### Предлагаемый вариант

Использовать один XLSX-файл, например:

```
/Фото дня/Задачи.xlsx
```

Каждая сохранённая задача становится новой строкой.

Пример:

| ID | Дата/время | Вид задачи | Сложность | Описание |
|---|---|---|---:|---|
| UUID | 29.09.2026 14:35 | Настройка | 3 | Настроил ... |
| UUID | 29.09.2026 15:10 | Анализ | 4 | Разобрал ... |

Поле **ID** рекомендую добавить сразу, хотя пользователь его не вводит. Оно позволит безопаснее обрабатывать повторную отправку записи после сетевой ошибки.

## 5. Как будет происходить сохранение XLSX

Важный момент: приложение не должно пытаться «дописать ячейку на Яндекс Диске» как в базу данных.

Предлагаемый процесс:

```
Пользователь нажимает «Сохранить»
        ↓
Формируем объект Task
        ↓
Получаем актуальный XLSX с Яндекс Диска
        ↓
Открываем XLSX на Android
        ↓
Добавляем новую строку
        ↓
Сохраняем изменённый XLSX во временный файл
        ↓
Загружаем новый XLSX обратно на Яндекс Диск
        ↓
Проверяем результат
        ↓
Показываем «Сохранено»
```

То есть источником истины остаётся файл на Яндекс Диске.

### Почему именно так

REST API Яндекс Диска позволяет работать с файлами, но нам нужна именно структура Excel-книги — строки, листы, ячейки. Поэтому Android-приложению понадобится библиотека для работы с XLSX.

Apache POI непосредственно поддерживает чтение и изменение XLSX, однако Android-использование требует специальной адаптации. citeturn1search6turn1search0

На первом этапе стоит сделать отдельный небольшой прототип:

1. скачать существующий `Задачи.xlsx`;
2. открыть его на Android;
3. добавить одну строку;
4. сохранить;
5. загрузить обратно на Яндекс Диск;
6. открыть файл на компьютере и проверить его целостность.

**Этот прототип является критической технической проверкой до разработки всего UI.**

## 6. Библиотеки

### Android

- Kotlin;
- Android SDK;
- Jetpack Compose;
- AndroidX ViewModel;
- Kotlin Coroutines;
- Navigation Compose — если понадобится несколько полноценных экранов;
- DataStore Preferences — для настроек приложения.

### HTTP

Предлагаю:

- **OkHttp** — HTTP-клиент;
- **Retrofit** — описание REST API Яндекс Диска;
- Kotlin Coroutines для асинхронных запросов.

При этом отдельный SDK Яндекс Диска тоже существует для Java/Android. Яндекс публикует Android SDK для работы с REST API. citeturn1search4turn1search7

Однако для нового приложения я предлагаю сначала рассмотреть прямую работу с REST API через OkHttp/Retrofit. Это уменьшает зависимость от старого SDK и позволяет контролировать именно те операции, которые нам нужны.

### XLSX

Основной вариант для прототипа:

**Apache POI / Android-совместимая сборка POI.**

Apache POI предоставляет полноценные API для чтения, изменения и записи XLSX. citeturn1search6

Есть и современные Android-ориентированные библиотеки XLSX, но их нужно отдельно проверять по лицензии, стабильности и совместимости с нашим сценарием. Например, DroidXLS позиционируется как Kotlin/Android-библиотека для XLSX, но имеет отдельные лицензионные условия для коммерческого использования. Поэтому автоматически брать её в проект пока не следует. citeturn1search5

## 7. Авторизация Яндекс

Для доступа к личному Яндекс Диску приложение должно получить OAuth-доступ.

Яндекс прямо предусматривает использование REST API в мобильных приложениях и требует OAuth-токен для доступа к пользовательским данным. citeturn1search3

Предлагаемый сценарий:

```
Настройки
   ↓
«Подключить Яндекс Диск»
   ↓
OAuth-авторизация Яндекс
   ↓
Получение access token
   ↓
Сохранение токена в защищённом хранилище Android
   ↓
Работа приложения с API
```

Пароль Яндекса в приложении хранить не нужно.

Access token нельзя хранить в обычном текстовом `SharedPreferences` или в файле настроек.

Для токена следует использовать Android Keystore / защищённое хранилище.

## 8. Настройки Яндекс Диска

Пользователь должен один раз указать:

- подключённый Яндекс-аккаунт;
- путь к таблице;
- имя XLSX-файла.

Например:

```
Папка: /Фото дня/
Файл: Задачи.xlsx
```

Лучше хранить не только отображаемый путь, но и канонический путь файла в формате API.

При первом запуске можно предложить:

**«Создать новую таблицу»**

Если файла нет:

1. приложение создаёт базовый XLSX;
2. добавляет заголовки;
3. загружает его на Яндекс Диск.

---

## 9. Модель задачи

Не привязывать модель задачи напрямую к колонкам Excel.

Предлагается модель:

```Task
- id: UUID
- createdAt: Instant
- type: TaskType
- difficulty: Int
- description: String
```

Но архитектура должна предусматривать расширение:

```Task
- стандартные поля
- набор дополнительных атрибутов
```

Например, позже может появиться:

- ссылка на Redmine;
- признак «инициировал сам»;
- затраченное время;
- результат;
- комментарий;
- проект;
- дополнительные оценки.

---

## 10. Редактируемый список видов задач

Вид задачи нельзя зашивать в код.

Нужна отдельная сущность:

```
TaskType
- id
- name
- sortOrder
- enabled
```

Пользователь сможет:

- добавить вид;
- переименовать;
- удалить/отключить;
- менять порядок.

Для первого варианта список видов можно хранить локально как настройки приложения.

Это не является хранилищем рабочих записей: **рабочие записи остаются в XLSX на Яндекс Диске**.

В будущем, если потребуется переносить список видов между устройствами, его можно также сохранять в отдельном файле на Яндекс Диске.

---

## 11. Сложность

Сложность — целое число:

```
0 1 2 3 4 5
```

UI лучше сделать в виде пяти/шести легко нажимаемых элементов, а не обычного текстового поля.

Важно не интерпретировать оценку автоматически.

Это именно субъективная самооценка сложности:

- 0 — практически без сложности;
- 5 — максимально сложная задача.

Промежуточные значения остаются ощущением пользователя.

---

## 12. Надёжность сохранения

Это один из наиболее важных элементов архитектуры.

Сценарий:

```
Пользователь нажал «Сохранить»
        ↓
Интернет пропал
        ↓
Не показываем «успешно»
        ↓
Запись не должна потеряться
```

Поэтому перед отправкой запись должна иметь уникальный ID.

После ошибки приложение может повторить операцию.

При повторной попытке:

1. скачать актуальный XLSX;
2. проверить наличие строки с таким ID;
3. если строки нет — добавить;
4. если есть — считать запись уже сохранённой.

Это уменьшает риск появления дублей.

---

## 13. Что делать при одновременном изменении файла

Есть фундаментальное ограничение выбранной схемы.

Если одновременно:

- телефон скачал XLSX;
- пользователь изменил тот же XLSX на компьютере;
- телефон затем загрузил свою изменённую копию;

можно потерять изменения компьютера.

Поэтому в архитектуре нужно явно учитывать конфликт версий.

Для первой версии предполагается сценарий **одного пользователя и одного основного устройства**, что значительно снижает риск.

Перед каждой записью приложение должно получать свежую версию файла с Яндекс Диска, а не держать старую копию как источник истины.

Если позже потребуется работа с нескольких устройств, понадобится отдельный механизм синхронизации/разрешения конфликтов.

---

## 14. Не использовать WebDAV как основной вариант

У Яндекс Диска есть WebDAV API, позволяющий обращаться к Диску как к файловой системе. citeturn0search2

Однако для приложения предлагаю использовать **REST API**, а не WebDAV.

Причины:

- REST API предназначен для программной работы приложений;
- проще явно контролировать операции;
- проще обрабатывать ошибки;
- проще отделить авторизацию, скачивание и загрузку;
- меньше зависимости от поведения файловой системы.

WebDAV оставить как резервный вариант исследования, если REST API даст проблему, которую сложно решить.

---

## 15. Синхронизация

На первом этапе не нужна постоянная фоновая синхронизация.

Нужна операция:

**«Сохранить задачу»**

и, возможно, отдельная:

**«Повторить отправку»**.

Если позже появится необходимость автоматически отправлять записи после восстановления интернета, можно добавить Android WorkManager. Он предназначен именно для надёжного выполнения отложенных асинхронных задач с учётом условий выполнения. citeturn0search8

Но включать его в первую версию без необходимости не стоит.

---

## 16. Локальное хранение

Не использовать Room как основную БД.

Рабочая запись должна считаться сохранённой только после успешной записи в XLSX на Яндекс Диске.

Допустимо временное локальное хранение:

- черновика;
- файла XLSX во время обработки;
- очереди неотправленных записей после ошибки.

Это технический кеш, а не альтернативное хранилище данных.

## 19. Ошибки, которые должны быть предусмотрены

Пользователь должен получать понятные сообщения как минимум для:

- нет авторизации Яндекс;
- истёк/недействителен токен;
- нет интернет-соединения;
- файл не найден;
- нет прав на файл;
- ошибка скачивания;
- XLSX повреждён или имеет неподдерживаемую структуру;
- ошибка изменения XLSX;
- ошибка загрузки;
- файл изменился между операциями;
- неизвестная ошибка API.

Не показывать пользователю сырые HTTP-ответы как единственное сообщение.

---

## 20. Самая важная техническая проверка перед полноценной разработкой

До создания сложного интерфейса необходимо подтвердить связку:

**Android → OAuth Яндекс → REST API → скачать XLSX → изменить XLSX → загрузить XLSX обратно.**

Если эта цепочка работает стабильно, остальная часть приложения относительно стандартна.

Поэтому **Шаг 2** целесообразно начать не с красивого интерфейса, а с минимального Android-прототипа:

1. подключение Яндекс;
2. выбор/задание пути к XLSX;
3. скачивание;
4. добавление тестовой строки;
5. обратная загрузка;
6. повторное скачивание;
7. проверка, что строка действительно сохранилась.

Только после успешного прохождения этого теста делать основной UI.

## 21. Предварительное решение

### Выбираем

- Android;
- Kotlin;
- Jetpack Compose;
- MVVM + разделение на presentation/domain/data;
- Coroutines;
- OkHttp + Retrofit для REST API;
- OAuth Яндекс;
- Android Keystore для чувствительных данных;
- XLSX как формат таблицы;
- Яндекс Диск как основное хранилище;
- временный локальный файл только для обработки XLSX;
- UUID у каждой записи;
- актуальная загрузка XLSX перед изменением;
- повторная проверка ID при повторной отправке.

### Пока не выбираем

- Firebase;
- Google Drive;
- собственный сервер;
- Room как основную БД;
- WebDAV как основной API;
- постоянную фоновую синхронизацию;
- сторонний платный Excel SDK без проверки лицензии.

## 22. Главный риск проекта

Главный риск находится не в Android UI.

Он находится в операции:

**«безопасно изменить существующий XLSX, находящийся на Яндекс Диске, и вернуть его обратно, не потеряв уже имеющиеся данные».**

Поэтому именно эту часть нужно подтвердить рабочим прототипом первой.

Если прототип покажет проблемы с Apache POI на целевых версиях Android, тогда отдельно выбираем другой XLSX-движок. Само архитектурное решение при этом сохраняется:

**Яндекс Диск → XLSX → изменение строки → XLSX → Яндекс Диск.**
