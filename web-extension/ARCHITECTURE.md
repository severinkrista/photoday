# Архитектура «Фото дня»

Android-приложение и браузерное расширение работают с одним authoritative source: photoday.xlsx на Яндекс Диске.

## Слои

UI -> application/repository -> платформенный adapter -> Яндекс Disk REST API / XLSX.

TaskRecord — единая логическая модель записи: ID, дата, время, день недели, часть дня, вид задачи, задача, сложность, папка вложения, файл вложения.

Настройки имеют единый смысл: режим отображения, количество задач/дней, путь к XLSX, типы задач.

## Что не нужно дублировать

Не копируем Android UI в браузер и браузерный UI в Android.

Будущая аналитика должна получать TaskRecord из repository и быть независимой от конкретного экрана.

Правила предметной области вроде части дня, типов задач, формата имени вложения и расчёта следующего ID должны оставаться единым контрактом и проверяться тестами каждой платформы.

Момент записи — тоже единый контракт: дата и время выбираются в форме добавления (в том числе задним числом), а день недели и часть дня выводятся из них. В Android это `domain/TaskMoment.kt`, в расширении — `src/datetime.ts`.

## Что допустимо дублировать

Yandex API adapter и XLSX adapter являются платформенными реализациями. Android использует Kotlin и собственный XlsxCodec, браузер использует TypeScript и XLSX-библиотеку.

Это нормальная граница ответственности: искусственное объединение Kotlin и TypeScript исходников ухудшило бы поддержку.

## Authoritative source

XLSX на Яндекс Диске остаётся источником истины.

Локальные pending-записи — только очередь неотправленных изменений. После успешной записи в XLSX они удаляются.

## Напоминания

Настройки напоминаний (диапазон времени, частота, вкл/выкл) — часть `AppSettings`.
Service worker (`src/background.ts`) держит `chrome.alarms`-будильник с периодом из настроек и
показывает `chrome.notifications`-уведомление только внутри диапазона и не чаще заданной частоты
(время последнего уведомления хранится в `storage.local`).

Кнопка «ОК» в уведомлении открывает окно плагина для ввода новой записи: сначала через
`chrome.action.openPopup()` (Chrome 127+), при недоступности — отдельным окном
`popup.html?new=1`. Кнопка «Отмена» ничего не открывает. Открытие из напоминания помечается
флагом в `storage.session`, поэтому попап сразу разворачивается и ставит курсор в поле описания.

Момент уведомления не зависит от того, есть ли в таблице записи: это просто приглашение
описать завершённые задачи.

## Окно плагина

Размер popup пользователь задаёт сам: уголок в правом нижнем углу (`#resizeHandle` в `popup.html`)
растягивает окно перетаскиванием, двойной клик возвращает 720×600. Границы — от 320×460 до 800×600:
верхняя совпадает с предельным размером popup в Chrome, поэтому окно не «уезжает» за экран,
нижняя оставляет под формой видимый список задач.

Форма новой записи держится компактной, чтобы умещаться в максимальное окно. Раскладка строк:
виды задач кнопками и сложность — в одной строке (звёздочки прижаты вправо), ниже описание задачи,
а в строке действий слева направо идут «Сохранить», компактная кнопка даты-времени и плашка
вложения у правого края. Раскрытый редактор даты и времени встаёт прямо под строкой действий.
Файловый input визуально скрыт внутри плашки, поэтому диалог выбора открывает сама плашка.
В узком окне (320 px) кнопки видов задач переносятся по строкам — форма остаётся читаемой.

Виды задач выводятся кнопками (первый десяток — то, что чаще всего нужно), остальные выбираются
из компактного выпадающего списка с подписью «ещё N ▾»; лимит задан константой `TYPE_CHIPS_LIMIT`
в `src/popup.ts`. Выбранный код хранится в состоянии окна, поэтому вид задачи уходит в запись
одинаково и при выборе кнопкой, и при выборе из списка.

Кнопка 📄 в шапке окна открывает саму таблицу. Адрес берётся из настройки «Ссылка для кнопки
«Открыть таблицу»» (`fileUrl`) — там может быть ссылка на редактор Яндекс Документов; если она
пустая, используется путь `diskPath`, открытый в веб-интерфейсе Яндекс Диска (`workbookUrl`
в `src/model.ts`). Та же кнопка есть на странице аналитики.

Выбранный размер хранится в `storage.local` под ключом `popupSize` (`getPopupSize`/`savePopupSize`
в `src/storage.ts`) и дублируется в `localStorage` страницы: кэш читается синхронно, поэтому окно
открывается сразу нужного размера, без скачка от размера по умолчанию. Применение размера —
в `src/popup.ts` (`applyPopupSize`), там же задано поведение режима «окно новой записи»: в `expanded`
страница занимает всё окно, а размер из настроек не применяется.

## Аналитика

Аналитика вынесена на отдельную страницу расширения (`analytics.html`) — в popup 800×600 графики не помещаются.
Данные берутся из того же authoritative source: `repository.getTasks()` читает XLSX с Яндекс Диска,
неотправленные записи из очереди могут быть добавлены переключателем.

Правила расчёта — в `src/analytics-engine.ts`, это зеркало Android-версии (`analytics/AnalyticsEngine.kt`):
те же группировки (день, неделя, месяц, день недели, часть дня, вид задачи, сложность, задача) и показатели
(количество, сумма/средняя/минимальная/максимальная сложность), поэтому цифры на платформах совпадают.
Расширение добавляет фильтры по периоду, части дня, дню недели, тексту задачи и вложениям.
Записи без даты в аналитику не попадают — как и в Android-версии.

Визуализация — Chart.js (`chart.js`, зафиксированная версия в package.json). Регистрируются только нужные
компоненты (bar/line/doughnut/pie, категориальная и линейная шкалы, легенда, подсказки), библиотека
подключается в бандл esbuild и не использует `eval`, поэтому подходит для CSP Manifest V3.
Тепловая карта активности рисуется на DOM — это не график, а календарная сетка со ссылками на день.

Проверяемость: `src/analytics-engine.ts` покрыт тестами на эталонных данных,
а конфигурации графиков проверяются сборкой бандла с подменённой Chart.js.

## OAuth

Браузер использует OAuth PKCE без client_secret. Токен хранится в browser extension storage и не передаётся на собственный сервер.

## Будущая аналитика

Рекомендуемый поток:

repository -> TaskRecord[] -> analytics services -> analytics UI

Например, отдельный TaskStatisticsService может считать количество задач, распределение сложности, типы, нагрузку по дням и динамику по периодам.

## Конкурентное редактирование

Android и browser сейчас работают по схеме read-modify-write. При одновременном редактировании файла Excel возможна гонка.

Перед массовым развитием стоит добавить optimistic concurrency: перед upload проверять состояние файла и не затирать изменения другого клиента.


## Автоматический учёт активности браузера (1.0.0)

Service worker в `src/autotrack.ts` отслеживает URL и заголовок активной вкладки, время начала сеанса и его длительность. Содержимое страниц и сообщений не считывается. URL очищается от query-параметров, названия которых похожи на токены, секреты, пароли, сессии, ключи или коды авторизации; фрагмент URL удаляется.

События и сеансы хранятся локально в `chrome.storage.local` в сериализуемой JSON-структуре `autotrackJson`. Сборщик фиксирует только активную вкладку, учитывает потерю фокуса окна и состояние простоя. Контрольная запись раз в минуту помогает не засчитывать длительность, пока браузер закрыт.

Периодическая отправка настраивается в параметрах расширения. По умолчанию — каждые 60 минут. Папка назначения по умолчанию — `disk:/Итоги дня`; для каждого дня создаётся `<корень>/<YYYY-MM-DD>/autotrack/autotrack.json`. Выгрузка содержит только сеансы длительностью **строго больше 180 секунд**. Файл дня перезаписывается свежей сводкой, поэтому на один день приходится один JSON. Если передача не удалась, локальные данные остаются и будут повторно отправлены при следующей попытке.

Разрешения `tabs` и `idle` добавлены в manifest для получения адреса/заголовка вкладки и определения простоя. Интервал передачи можно изменить от 5 до 1440 минут, сбор можно отключить в настройках.
